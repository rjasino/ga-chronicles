# Database maintenance: local and production Supabase

Runbook for instructors and maintainers configuring this repository's Supabase database during development and managing the hosted production project. The local stack is disposable development infrastructure; the hosted project contains real data and must only be changed deliberately.

## Safety rules

- Keep schema changes in reviewed SQL migrations under `supabase/migrations/`. Test each change locally before applying it to a hosted project.
- Confirm the hosted project's name and project reference in the Supabase Dashboard before every remote operation. Existing repository notes have referenced `segycgobrqtlizaqtwhl` as Game Ako Chronicles; treat that as a hint and verify it is still the intended production project.
- Never run `supabase db reset` against production; it is a destructive local-development command that deletes the local database and reapplies migrations and `supabase/seed.sql`.
- Never include local seed data in a production push. Do not use `--include-seed` or `--include-all` unless an authorized maintainer has reviewed the exact effect.
- Never commit `.env.local`, production credentials, database passwords, service-role keys, or database exports. Store production secrets only in the approved deployment secret store and protected backup storage.
- Supabase's anon/publishable key is intended for browser use only when Row Level Security (RLS) is correctly configured. A service-role key bypasses RLS and must remain server-side.

## Local development database

### Prerequisites and project settings

- Docker Desktop is installed and running.
- Use Node.js `>=24 <25` as required by `apps/web/package.json`.
- The Supabase CLI is pinned to `supabase@2.122.0` in `apps/web/package.json` and `apps/web/package-lock.json`. Use the project scripts so a globally installed or newer CLI does not change the local image set.
- `supabase/config.toml` defines this local project as `game-ako-chronicles`, uses Postgres major version 17, and reserves ports `55320`–`55324`:

  | Service | Local address/port |
  |---|---|
  | API | `http://127.0.0.1:55321` |
  | Postgres | `127.0.0.1:55322` |
  | Studio | `http://127.0.0.1:55323` |
  | Local email capture | `127.0.0.1:55324` |
  | Database shadow port | `55320` |

These ports let this stack run beside another local Supabase project. Do not change them just to resolve a collision without first checking whether another project is using the range.

### Start and configure the local stack

Run these commands from the repository root:

```powershell
npm ci --prefix apps/web
npm --prefix apps/web run supabase:verify-version
npm --prefix apps/web run supabase:start
npm --prefix apps/web run supabase:status
```

Copy the local API URL, anon key, and service-role key reported by `supabase status` into the ignored `apps/web/.env.local`, using `apps/web/.env.example` as a template:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:55321
NEXT_PUBLIC_SUPABASE_ANON_KEY=<local-anon-key>
SUPABASE_SERVICE_ROLE_KEY=<local-service-role-key>
SITE_URL=http://localhost:3000
```

Use only keys generated by the local CLI here. Never copy production values into `.env.local`. Start the web app with `npm --prefix apps/web run dev`; use Studio to inspect the local database and Mailpit to inspect captured development email.

### Local migration and test workflow

1. Add schema changes as a new migration under `supabase/migrations/`; do not make an untracked schema-only change in Studio.
2. Apply the full migration history and seed to the disposable local database with `npm --prefix apps/web run supabase:reset`.
3. Run the relevant application and database tests, including `npm --prefix apps/web run test:database`.
4. Review the migration for correct RLS, grants, storage policies, and data preservation before committing it.

`supabase:reset` deletes local database data before replaying migrations and `supabase/seed.sql`. If local data matters, stop and make a backup first. `supabase stop` preserves local volumes; `supabase stop --no-backup` deletes them.

### Local image baseline and refresh

The following service tags were observed in the local Docker stack on 2026-11-21. The pinned CLI and local project configuration are authoritative; this table is a review aid after an intentional CLI upgrade.

| Service | Image tag |
|---|---|
| Postgres | `17.11.0.006` |
| Studio | `2026.10.19-sha-b375769` |
| Postgres Meta | `v0.100.0` |
| Edge Runtime | `v1.77.8` |
| Storage API | `v1.84.19` |
| PostgREST | `v16.5` |
| Realtime | `v2.147.1` |
| GoTrue (Auth) | `v2.197.0` |
| Kong | `2.8.1` |
| Mailpit | `v1.31.3` |

Docker Desktop can show multiple tags for a service when a newer CLI has downloaded images but the existing containers still use the previous tags. `supabase start` may keep using the version pins stored in `supabase/.temp/*-version`. A status message such as `Stopped services: [imgproxy, analytics, vector, pooler]` is expected for services disabled or not enabled in `supabase/config.toml`.

Diagnose from the repository root:

```powershell
npm --prefix apps/web run supabase:version
npm --prefix apps/web run supabase:verify-version
npm view supabase version
npm --prefix apps/web run supabase:status
docker ps --format "table {{.Names}}\t{{.Image}}"
docker images --format "{{.Repository}}:{{.Tag}}" | Select-String supabase
Get-ChildItem supabase\.temp -Filter *-version |
  ForEach-Object { "$($_.Name) = $(Get-Content $_.FullName -Raw)" }
```

To refresh local images while retaining the database volume, stop the stack, clear only image-version pins, and restart:

```powershell
npm --prefix apps/web run supabase:stop
Get-ChildItem supabase\.temp -Filter *-version | Remove-Item -Force
npm --prefix apps/web run supabase:start
npm --prefix apps/web run supabase:status
```

Do not delete `supabase/.temp/` wholesale: it contains machine-specific CLI metadata. If an upgrade changes the Postgres **major** version, do not use the image-refresh procedure as a database upgrade. Back up first, then follow a planned migration/restore or reseed procedure. The local `[db].major_version` is 17; verify the hosted project's major version separately before planning a major upgrade.

After verifying the new stack, identify unused Supabase image tags and remove only the specific stale tags with `docker rmi <tag>`. Do not use `docker image prune -a`: it can remove images used by other projects and tools, including `pg_prove` and analytics services.

### Local verification and Windows port issue

Confirm the containers are healthy and the API responds:

```powershell
npm --prefix apps/web run supabase:status
docker ps --format "table {{.Names}}\t{{.Image}}"
(Invoke-WebRequest -Uri "http://127.0.0.1:55321/rest/v1/" -UseBasicParsing).StatusCode
```

If Docker reports that a port is unavailable, first check for another local Supabase stack using the `553xx` range. On Windows, a message such as `forbidden by its access permissions` may instead indicate a Hyper-V excluded port range:

```powershell
netsh int ipv4 show excludedportrange protocol=tcp
```

If `55320`–`55324` overlap a reserved range, an administrator can restart WinNAT:

```powershell
net stop winnat /y
net start winnat
```

Retry the local `supabase:start` script. The reservation may return after a reboot, Docker Desktop update, or WSL/Hyper-V network change.

### Keep the CLI predictable

Run the Supabase scripts from this repository, for example:

```powershell
npm --prefix apps/web run supabase:verify-version
npm --prefix apps/web run supabase:start
npm --prefix apps/web run supabase:status
npm --prefix apps/web run supabase:reset
npm --prefix apps/web run test:database
```

For CLI commands without an npm script, use the pinned dependency from the repository root:

```powershell
npm --prefix apps/web exec -- supabase <command>
```

Avoid bare `npx supabase` from the repository root because it can resolve a different CLI version. Run `npm ci --prefix apps/web` after dependency changes, then `supabase:verify-version`. Upgrading the CLI is deliberate: update the exact dependency, review the lockfile, verify the new version, and review the changed local image tags.

Do not run `supabase link` for ordinary local development. Linking changes the local project metadata and can affect which hosted project is targeted by later CLI commands.

## Hosted production Supabase

### Configure and protect the hosted project

Use the Supabase Dashboard to create or confirm the dedicated production project. Before continuing, verify its organization, project name, region, project reference, and Postgres major version with the project owner. Keep staging/preview environments separate from production where possible. Do not connect the local Docker stack to production credentials.

In the hosted project's Dashboard:

1. Set up the database and its approved backup/recovery plan. Record the database owner, incident contact, expected retention, quota review owner, and restore procedure.
2. Configure Authentication's **Site URL** to the canonical production origin and add the exact production OAuth callback URL, `https://<production-domain>/auth/callback`, to the allowed redirect URLs. Configure the production identity provider and SMTP according to the organization's policy. Do not use local `localhost` callback URLs as production redirects.
3. Apply the repository migrations to create the app schema, RLS policies, and storage buckets. The current migrations create the `article-covers` and `article-images` buckets; review the matching storage policies in the migrations rather than recreating them manually in the Dashboard.
4. Verify RLS and grants for application tables. Do not disable RLS to work around an application error. Treat Dashboard SQL changes as temporary and immediately capture any intended schema change in a reviewed migration.
5. Keep service-role and database credentials restricted to authorized operators. Enable the platform's available monitoring and alerts for database capacity, storage, egress, and project health.

Set deployment environment variables in the hosting provider's protected environment settings, not in Git:

| Variable | Production value/use |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | The verified hosted project's HTTPS API URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | That project's anon/publishable key; browser-visible, protected by RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | That project's service-role secret; server-only, never expose to browser code |
| `SITE_URL` | The canonical production site origin |

Set the production values only in the production deployment environment. Use a separate Supabase project and separate variables for previews when available. Rotate any secret that was exposed or committed.

### Apply reviewed migrations to production

Only an authorized maintainer should run this procedure. Complete a local reset and relevant tests first, review the migration diff, and confirm a recent recoverable backup. From the repository root, authenticate the pinned CLI with the appropriate Supabase account, then link this checkout to the verified production project:

```powershell
$projectRef = "<verified-production-project-ref>"
npm --prefix apps/web exec -- supabase link --project-ref $projectRef
```

Linking updates local CLI metadata; it does not change the hosted database. Before any mutation, verify the target in the Dashboard and inspect the remote migration history and planned changes:

```powershell
npm --prefix apps/web exec -- supabase migration list --linked
npm --prefix apps/web exec -- supabase db push --dry-run --linked
```

Stop if the project reference, migration history, or dry-run output is unexpected. After review and explicit production approval, apply only the pending migrations:

```powershell
npm --prefix apps/web exec -- supabase db push --linked
npm --prefix apps/web exec -- supabase migration list --linked
```

Review the CLI's target and confirmation prompt before accepting. Do not add `--include-seed` for production. Verify the app's critical read/write flows, authentication redirects, RLS behavior, and storage uploads after the migration. Keep a release record with the project reference, commit, migrations applied, backup status, and verification results.

The CLI's `supabase db dump` default is **not** a complete Supabase backup: the default dump contains schema but no data and excludes Supabase-managed schemas such as Auth and Storage. A data-only dump still does not back up Auth identities or Storage objects. Use the hosted plan's backup facilities and separately plan for any required Auth, Storage, and external exports; test restoring into a separate project. Store exports encrypted and outside the repository. Never treat a SQL dump alone as proof that the whole project can be recovered.

### Ongoing production maintenance

- Review Supabase plan limits, database health, storage, egress, and auth/provider configuration at least monthly and before a major release.
- Verify scheduled backups and periodically rehearse a restore into a separate project. Preserve any required article images and other Storage objects outside the primary project.
- Deploy additive, backward-compatible migrations before application code that depends on them. For destructive or large data migrations, plan and verify a staged migration and recovery path.
- Keep production access limited to named maintainers. Review and rotate privileged credentials when access changes or exposure is suspected.
- Do not run local reset, local seed, local image refresh, or Docker cleanup procedures against a hosted project; those operations have separate local/remote semantics.

## Quick reference

| Symptom | Meaning | Action |
|---|---|---|
| Two Supabase image tags per service in Docker Desktop | New image downloaded; existing local containers still use the pinned tag | Refresh local image pins as described above, then remove stale tags individually |
| `Stopped services: imgproxy, analytics, vector, pooler` | Optional local services are disabled | Ignore unless the project configuration has changed |
| Local port unavailable on `553xx` | Another stack or a Windows excluded port range | Check running containers and `netsh int ipv4 show excludedportrange protocol=tcp` |
| `supabase:verify-version` fails | Manifest, lockfile, or installed CLI versions differ | Run `npm ci --prefix apps/web`, then verify again |
| Local database will not start after a Postgres major upgrade | Existing volume uses a different Postgres major | Back up and plan a proper restore/reseed; do not delete data blindly |
| Remote migrations are unexpected | Wrong project linked or migration history drifted | Stop; verify the Dashboard project ref and reconcile migration history with the database owner |
| Production backup exists but restore has not been tested | Recoverability is unverified | Schedule a restore test in a separate project before relying on it |
